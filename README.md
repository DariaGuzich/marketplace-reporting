# marketplace-reporting

Reporting: принимает события от Serving и считает почасовые агрегаты по аккаунтам.

```
marketplace-serving ──POST /events──► marketplace-reporting (этот репозиторий) ──► PostgreSQL, схема reporting
                                              │ каждый час в :05 — агрегация предыдущего часа
                                              ▼
                                       GET /reports/{account_id}
```

## API

| Метод | Путь | Что делает |
|---|---|---|
| POST | `/events` | принять событие; дубль по `event_id` не сохраняется |
| POST | `/admin/aggregate?hour=2026-10-01T10:00:00Z` | посчитать агрегаты за час вручную; 400, если это не целый час |
| GET | `/reports/{account_id}` | агрегаты аккаунта по часам |

```json
POST /events
{ "event_id": "3f2c...", "account_id": "acc-1", "timestamp": "2026-10-01T10:15:00Z", "shown": true }
→ { "stored": true }      // повтор того же event_id → { "stored": false }, тоже 200

GET /reports/acc-1
→ [ { "hour": "2026-10-01T10:00:00Z", "requests": 120, "shown": 87 } ]
```

Все времена в UTC. Час `10:00` — события с `10:00:00` включительно до `11:00:00` не включительно.

## Как устроено

**Хранение** — схема `reporting` в той же базе PostgreSQL, что у API. У Reporting свои миграции Flyway и своя
таблица `reporting.flyway_schema_history`. С таблицами API в схеме `public` он не пересекается.

| Таблица | Что в ней |
|---|---|
| `events` | сырые события, первичный ключ — `event_id` |
| `hourly_stats` | агрегаты: одна строка на `(account_id, hour)` |

**Дубли событий.** Serving при ошибке отправляет событие ещё раз с тем же `event_id`. Ошибка может случиться
уже после того, как Reporting сохранил событие (например, истёк таймаут ответа). Поэтому событие сохраняется
так: `INSERT ... ON CONFLICT (event_id) DO NOTHING`. Второй раз то же событие не запишется.

**Агрегация** (`ReportingRepository.aggregateHour`) — один SQL-запрос:

```sql
INSERT INTO hourly_stats (account_id, hour, requests, shown)
SELECT account_id, :hourStart, count(*), count(*) FILTER (WHERE shown)
FROM events
WHERE event_time >= :hourStart AND event_time < :hourEnd
GROUP BY account_id
ON CONFLICT (account_id, hour) DO UPDATE SET requests = EXCLUDED.requests, shown = EXCLUDED.shown
```

Агрегаты за час каждый раз **пересчитываются заново из сырых событий и заменяют прежние**. Поэтому повторный
запуск за тот же час не удваивает цифры: результат тот же. Так агрегация становится идемпотентной.
Ошибочный вариант — прибавлять к прежнему значению (`SET requests = hourly_stats.requests + EXCLUDED.requests`):
тогда каждый повторный запуск удваивал бы цифры.

**Расписание** (`AggregationJob.aggregatePreviousHour`) — каждый час в :05 UTC агрегируется предыдущий полный
час (в 11:05 — час 10:00). 5 минут запаса нужны, чтобы события, отправленные в последние секунды часа, успели
дойти. Вручную та же работа запускается через `POST /admin/aggregate`.

## Позднее событие

Событие за 10:50 пришло в 11:30, а час 10:00 уже посчитан в 11:05.

**Как ведёт себя система:**
- событие сохраняется в `events`, как обычно;
- `hourly_stats` за 10:00 **не меняется**: отчёт показывает цифры без этого события;
- расписание считает только предыдущий час, поэтому к 10:00 само больше не вернётся. Событие попадёт в отчёт,
  только если кто-то запустит `POST /admin/aggregate?hour=...T10:00:00Z` ещё раз. Благодаря идемпотентной
  агрегации это безопасно.

**Как это решают в реальных системах:**
- пересчитывать по расписанию не один, а несколько последних часов (например, 24): поздние события до суток
  учитываются автоматически, и цена этого — повторная работа;
- при получении позднего события помечать его час как «грязный» и пересчитывать только такие часы;
- в потоковой обработке (Kafka Streams, Flink) — «водяной знак» (watermark) и допустимое опоздание
  (allowed lateness). События опоздавшие сильнее отбрасываются или идут отдельным потоком;
- помечать отчёт за час как «предварительный», пока не прошло окно опоздания.

## Почему расписание не тестируется ожиданием

Тест «запустить приложение и подождать до :05» шёл бы до часа, зависел бы от времени запуска и всё равно
проверял бы в основном то, что Spring умеет вызывать методы по cron. Поэтому работа разделена на две части,
и каждая тестируется отдельно:

| Что | Как тестируется |
|---|---|
| **сама агрегация** `aggregate(hour)`: что и как считается | `ReportingApiTest` — события с заданными метками, вызов агрегации за конкретный час, проверка сумм |
| **выбор часа при запуске по расписанию** | `AggregationJobTest` — часы «заморожены» (`Clock.fixed` на 11:05), метод, который вызывает планировщик, вызывается напрямую → проверяем, что выбран час 10:00 |
| **сам cron** (`0 5 * * * *`) | не тестируется: это настройка Spring. Проверяется один раз вручную или по логу `Aggregated hour ...` |

Ключевое для этого — **код берёт текущее время только из бина `Clock`**, а не из `Instant.now()`. Тогда в тесте
можно подставить любое «сейчас», в том числе неудобное: полночь, смену дня, переход на летнее время.

## Запуск

Нужны Java 21, Maven и PostgreSQL из marketplace-infra (`docker compose up -d`). Схему `reporting` Flyway
создаст сам при первом запуске.

```bash
mvn spring-boot:run       # порт 8082
```

| Переменная | По умолчанию | Что это |
|---|---|---|
| `PORT` | `8082` | порт |
| `DB_URL`, `DB_USER`, `DB_PASSWORD` | база из docker-compose | PostgreSQL |
| `AGGREGATION_CRON` | `0 5 * * * *` | расписание агрегации (секунды минуты часы ...), UTC |

Чтобы увидеть запуск по расписанию, не дожидаясь часа: `AGGREGATION_CRON="0 * * * * *"` — каждую минуту
(будет агрегироваться предыдущий час).

## Тесты

```bash
mvn verify      # нужен Docker
```

| Тест | Что проверяет |
|---|---|
| `ReportingApiTest.aggregatesOnlyEventsOfGivenHour` | границы часа: 09:59:59 и 11:00:00 не входят, 10:00:00 входит; суммы `requests` и `shown` |
| `ReportingApiTest.duplicateEventIsStoredOnce` | тот же `event_id` дважды → `stored: false`, в агрегате 1 |
| `ReportingApiTest.rerunOfAggregationDoesNotDoubleCounts` | два запуска за один час → те же цифры |
| `ReportingApiTest.lateEventIsCountedOnlyAfterHourIsAggregatedAgain` | позднее событие не видно, пока час не пересчитан |
| `ReportingApiTest.aggregationRejectsNotWholeHour` | `hour=10:30` → 400 |
| `AggregationJobTest` | запуск по расписанию в 11:05 → час 10:00; в 00:05 → 23:00 предыдущего дня |

## Сознательные упрощения

- Агрегация — один SQL-запрос по всем событиям часа. На больших объёмах так не делают: события хранят
  в колоночных хранилищах (ClickHouse, BigQuery) или считают потоково.
- Сырые события хранятся вечно, таблица не разбита на партиции по времени.
- Если запустить несколько экземпляров Reporting, расписание сработает в каждом. Агрегация идемпотентна,
  поэтому вреда не будет, только лишняя работа. Обычно ставят распределённую блокировку (например, ShedLock).
- Пропущенный запуск по расписанию (Reporting был выключен в :05) никто не догоняет: час остаётся
  непосчитанным, пока его не запустят вручную.
- Время события — время Serving. Если часы Serving врут, событие попадёт не в тот час.

## Инструменты

- **Spring Boot**: HTTP, `@Scheduled` с cron, `JdbcClient`.
- **PostgreSQL**: `ON CONFLICT` для дедупликации и идемпотентной агрегации, `count(*) FILTER (WHERE ...)`.
- **Flyway** — миграции своей схемы `reporting`.
- **`java.time.Clock`** — подменяемое «сейчас» для тестов расписания.
- **Testcontainers** — настоящий PostgreSQL в тестах. **RestAssured** — API-тесты.
